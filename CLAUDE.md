## Commandes

- `npm run dev`, `npm run build`, `npm run typecheck`, `npm run lint`, `npm run format`
- `npm test` : Vitest, projet `unitaires`, fichiers `src/**/*.test.ts` sauf `*.integration.test.ts`. Sans base
- `npm run test:integration` : Vitest, projet `integration`, fichiers `src/**/*.integration.test.ts`. Avec base : refuse toute base sans la marque de test
- `npm run test:e2e` : `scripts/e2e-base-jetable.mjs`, puis Playwright, dossier `e2e/`, sur le site construit (`next start`, en local comme en CI). **Hors CI, base PostgreSQL 18 jetable dans Docker** (port sur `127.0.0.1`, préparée comme la CI, supprimée même après un échec ou un Ctrl+C) : **Docker démarré** ; secours sur `dev` : `E2E_BASE=dev npm run test:e2e`. En CI (`CI` défini), Playwright tel quel sur le service du workflow. Sortie des deux serveurs dans `.e2e-journaux/` (`docs/features/e2e-base-jetable.md`). **Toujours `npm run build` avant** : sinon les tests visent l'ancienne construction. **Ports 3000 et 3101 libres** (`netstat -ano | grep -E ":(3000|3101) "`) : `reuseExistingServer` est à `false`, un serveur déjà lancé fait échouer la suite au lieu d'être réutilisé. Le port 3101 sert le second serveur, configuration factice et base injoignable (`e2e/serveur-panne.ts`). Deux projets : `mobile-390` (`accueil`, `affichage`, `affichage-360`, `inscription`, `connexion`, `affichage-connecte`, `mot-de-passe`, `double-authentification`, `profil-sessions`, `donnees-personnelles`) et `ordinateur-1280` (tout sauf `affichage-360`). Chaque serveur précharge `e2e/simuler-hibp.mjs` (Have I Been Pwned simulé, aucun appel réel) ; chaque serveur écrit sa sortie dans `.e2e-journaux/` (`e2e/lancer-serveur.mjs`), celle du serveur en panne relue par le test T-39 ; les comptes `e2e-<exécution>-<n>@exemple.invalid` sont supprimés en fin de suite (`e2e/nettoyer-comptes.ts`). La politique de sécurité du contenu diffère en développement (`docs/features/socle-interface.md`, sections 5.3 et 6)
- `npm run verifier` : enchaîne `format:check` (même commande que la CI), `lint`, `typecheck`, `test`, `build` et `test:e2e`, s'arrête au premier échec, puis échoue si le port 3000 ou 3101 est encore en écoute (`scripts/verifier-ports.mjs`, connexion sur `127.0.0.1` et `::1`). À lancer avant de dire qu'une tâche est terminée, ports libres au départ ; `npm run test:integration` s'y ajoute à part quand la base est concernée
- `npm run db:generate` puis lecture du SQL généré, puis `npm run db:migrate`
- `node scripts/verifier-connexion.mjs`, `verifier-tables.mjs`, `verifier-isolation.mjs`
- `npm run verifier:auth` : vérifie que Better Auth lit la base (tsx avec la condition `react-server`, requise par `server-only`)
- `node scripts/controle-deploiement.mjs <origine> [--essais 3] [--pause 20]` : contrôle après déploiement, GET publics sans secret, plus vingt POST sans corps ni `Origin` (statut, politique, en-têtes, fuites, texte du gabarit, `/tableau-de-bord` identique avec un cookie forgé, `/lien/devis/<jeton>` identique pour deux jetons, `/api/taches/quotidienne` sans secret et avec un secret forgé identique à une tâche inexistante, `/api/auth/organization/*`, `/api/auth/get-session`, le lien de Better Auth `/api/auth/reset-password/<jeton>` et `/api/auth/two-factor/get-totp-uri`, `/send-otp`, `/verify-otp`, `/api/auth/list-sessions` identiques à un chemin inexistant, `/compte`, `/compte/double-authentification`, `/compte/profil` et `/compte/sessions` identiques avec un cookie forgé, `/mot-de-passe-oublie`, `/lien/reinitialisation` et `/donnees-personnelles` contrôlées comme `/connexion`, les dix-neuf POST des comptes (inscription, renvoi, vérification, connexion, déconnexion, demande et réinitialisation du mot de passe, les sept de la double authentification, les quatre du profil et des sessions, et la nouvelle authentification `/api/auth/verify-password`) identiques au POST d'un chemin inexistant, donc comptes fermés, option `--detail`). En local, seuls les deux contrôles `comptes:*` échouent : les comptes ne sont fermés qu'en production. Code 0, 1 (échec) ou 2 (adresse refusée). Lancé par `.github/workflows/controle-deploiement.yml` après chaque déploiement de production. L'assistant ne le lance jamais contre la production ni une prévisualisation : seulement contre `http://localhost:<port>` (`docs/features/controle-deploiement.md`)

## Règles de sécurité (non négociables)

1. Ne lis, n'affiche et ne modifie jamais `.env.local`. N'écris aucun secret dans le code, les tests, les journaux ou les commits.
2. Aucun fichier de `src/` ne mentionne `DATABASE_URL_MIGRATION`. L'application n'utilise que `DATABASE_URL`, le rôle restreint `app_facturation`.
3. Toute table métier porte `organisation_id NOT NULL` et une règle de sécurité au niveau des lignes, activée et forcée. Modèle unique : `src/server/db/schema/isolation.ts` (`pgTable.withRLS`, `colonneOrganisation()`, `regleIsolation()`), plus un index dont `organisation_id` est la première colonne. Le forçage s'ajoute par une migration `--custom` (voir « Méthode de travail »). Chaque table appelle `verifierIsolation` dans son test d'intégration ; le test d'inventaire refuse toute table non conforme, et toute table sans `organisation_id` hors de `TABLES_SANS_ORGANISATION` (les tables de Better Auth et `compteur_debit`).
4. Toute requête passe par la couche d'accès aux données. `drizzle-orm` ne s'importe que dans `src/server/db/`. Aucune requête construite par concaténation. **Toute requête métier s'exécute dans `executerDansOrganisation`** (`src/server/db/client.ts`), qui fixe l'organisation active par `set_config('app.organisation_id', $1, true)` dans la transaction. Jamais `SET`, `SET LOCAL` ni `set_config(..., false)`. `db` ne s'importe que dans `src/server/auth/config.ts` et `src/server/db/` (règle ESLint).
5. Toute action serveur et toute route passe par la fonction commune de contrôle : origine, session, rôle, validation. Une action se déclare par `declarerAction` dans `src/server/actions/<domaine>.ts`, avec sa limite de débit (`debit`, nom de `src/server/debit/limites.ts` qui compte l'utilisateur, ou `null` explicite) et ses modèles d'email (`emails`, ou `[]` explicite), s'inscrit dans `registre.ts` avec son cas dans `registre.integration.test.ts` (sinon `npm run typecheck` échoue), et s'expose dans un fichier `"use server"` `src/app/**/actions.ts` sous la seule forme `export const x = exposer(declaration)`. Aucun `route.ts` hors de la liste admise de `src/server/actions/inventaire.test.ts`. Règles ESLint G à M et test d'inventaire : `docs/features/chaine-controles.md`, section 7. La matrice des droits vit dans un seul fichier (`src/server/autorisation/matrice.ts`). **Toute page de `src/app/(app)/` appelle `lirePourPage`** (`src/server/actions/exposer.ts`) dans son propre `page.tsx`, avec son droit, même si elle ne lit rien : le gabarit `(app)/layout.tsx` ne protège pas (il n'est pas réexécuté à chaque navigation). Sans session, sans adhésion ou sans droit : la page « introuvable », statut 404, la même réponse avec ou sans cookie forgé. S-02 porte sur les ressources (identifiants, jetons), qui passent toujours par une même route : une ressource refusée et une ressource absente reçoivent la même réponse. Le nom d'une page est public, jamais son contenu ; il n'est pas comparé à une adresse inexistante. **Toute page de `src/app/(compte)/`** (utilisateur connecté, sans organisation, 1.2) **appelle `lireComptePourPage`** dans son propre `page.tsx`, mêmes interdits (`docs/features/connexion.md`, section 5.1). Le test d'inventaire le vérifie. Aucune métadonnée propre ni `loading.tsx` dans `(app)/` : le titre fuirait sur la réponse « introuvable », et `notFound()` répondrait 200. Next.js 16.4 ne rend pas `not-found.tsx` sur le serveur après un `notFound()` : une page refusée reçoit son document d'erreur au corps vide, la page « introuvable » s'affichant après hydratation, alors qu'une adresse sans page reçoit la page rendue par le serveur, avec `next start` comme sur Vercel. Aucune route attrape-tout : constaté le 2026-10-13, Vercel sert quand même la page rendue à une adresse sans page, et une telle route ferait différer `next start` de la production (`docs/features/controle-deploiement.md`, section 5). Les entrées de navigation sont filtrées côté serveur (`entreesVisibles`, `src/server/autorisation/navigation.ts`) : une entrée refusée n'atteint jamais le navigateur. Fiche : `docs/features/socle-interface.md`, sections 2.3 et 2.4.
6. Un accès refusé reçoit la même réponse qu'une ressource inexistante (S-02).
7. Toute entrée externe est validée côté serveur par un schéma Zod. Le serveur recalcule les totaux et ignore ceux reçus.
8. Les montants sont des entiers en francs CFA. Aucun nombre à virgule flottante.
9. Un document émis, un paiement et le journal d'audit ne sont jamais modifiés ni supprimés. **Toute écriture au journal d'audit passe par `journaliser`** (`src/server/journal/audit.ts`), dans la transaction de l'action qu'elle décrit ; elle n'accepte que les actions de la liste fermée (`src/server/journal/actions.ts`) et des détails stricts, sans texte libre. `src/server/db/requetes/journal.ts` ne s'importe que depuis `audit.ts` (règle ESLint). Une table en ajout seul (aujourd'hui `journal_audit`) n'a ni `UPDATE`, ni `DELETE`, ni `TRUNCATE` pour le rôle de l'application (migration `retirer-droits-<table>`), figure dans `TABLES_AJOUT_SEUL` du test d'inventaire, et passe `verifierIsolation(..., { ajoutSeul: true })`.
10. Aucune nouvelle dépendance sans accord explicite : propose le nom exact, la raison et une alternative. Jamais `npm audit fix`. Composants shadcn par leur nom uniquement, jamais par une adresse.
11. Aucune route exposée, dont `/api/auth`, hors d'une fiche de fonctionnalité validée.
12. `process.env` ne se lit que dans `src/server/env.ts`. Les règles de validation vivent dans `src/server/env-schema.ts`, une fonction pure qui ne lit pas `process.env`. **Seule exception** : `src/proxy.ts` lit `process.env.NODE_ENV`, et cette seule propriété, pour choisir la politique de développement (règle B d'`eslint.config.mjs`, `docs/features/socle-interface.md`, section 5.5). `src/proxy.ts` n'importe jamais `server/env.ts` (règle S) : une variable invalide ferait échouer chaque requête.
13. Tout fichier de `src/server/` commence par `import "server-only";`, sauf ceux de `src/server/db/schema/` : drizzle-kit les charge hors de Next.js, et `auth.ts` est généré. Sous Vitest, un alias remplace `server-only` par `tests/stubs/server-only.ts`.
14. Le module `testUtils` de Better Auth (sessions sans mot de passe) n'existe que dans l'instance de test de `src/server/db/outils-test/membres.ts`. Jamais dans `optionsAuth` ni `auth` (`src/server/auth/config.ts`), même sous condition. Le mot `testUtils` n'apparaît dans `src/` que dans les tests et `outils-test/`, y compris dans les commentaires : `config.test.ts` le vérifie.
15. **Toute limitation de débit passe par `verifierDebit`** (`src/server/debit/debit.ts`), jamais pendant une transaction ouverte. Les limites ne vivent que dans `src/server/debit/limites.ts`. La clé d'un compteur est une empreinte HMAC, jamais une adresse IP, un email ou un identifiant en clair. `compteurDebit` ne s'importe que dans `src/server/db/debit.ts`, qui ne s'importe que dans `src/server/debit/` (règle ESLint N). Fiche : `docs/features/limitation-debit.md`.
16. **La politique de sécurité du contenu est posée par `src/proxy.ts`, seul fichier de proxy** (nonce neuf à chaque requête, `docs/features/socle-interface.md`, section 5) ; les autres en-têtes de sécurité, par `next.config.ts` depuis `src/lib/securite/entetes.ts` (section 6). Dans `src/` : aucun `dangerouslySetInnerHTML`, `innerHTML`, `document.write`, `srcDoc`, `<script>`, `next/script`, URL `javascript:` ni `eval` (règle O), aucun attribut `style` (règle P). Aucun script tiers. Les pages d'erreur n'affichent que `error.digest`, jamais le message, le nom, la pile ni la cause.
17. **Tout email passe par la porte d'envoi, `envoyerEmail`** (`src/server/email/envoi.ts`). Un service ne l'appelle jamais : il demande un envoi par `ctx.preparerEmail`, avec un modèle déclaré dans `emails` de son action, et la chaîne envoie après la validation de la transaction, limites `email.*` vérifiées à ce moment-là (jamais dans la transaction, règle 15). L'appelant ne fournit qu'un modèle de `src/server/email/modeles.ts`, un destinataire et des paramètres en briques fermées : ni expéditeur, ni sujet, ni corps, ni copie, ni en-tête, ni adresse de lien. Un lien n'a que deux formes, toujours sur l'origine de l'application : un chemin `/lien/` construit par la porte depuis un jeton (`lienPublic`, `lienFragment`), ou une page fixe d'une liste fermée (`lienPage`, `PAGES_LIEN` : `/connexion`, `/mot-de-passe-oublie`), écrite dans la construction du modèle, jamais fournie par l'appelant ; une page hors de la liste est refusée (`docs/features/mot-de-passe.md`, section 6.3). Texte brut, aucune donnée sensible, textes dans `src/textes/emails.ts`. Hors production (`VERCEL_ENV` différent de `production`), aucun envoi hors de `EMAIL_DESTINATAIRES_AUTORISES`. Jamais une adresse ni le message d'une erreur du transport dans un journal. `nodemailer` ne s'importe que dans `src/server/modules/email/smtp.ts`, `src/server/modules/email/` que dans `envoi.ts`, `envoyerEmail` que dans `src/server/actions/action.ts` (règle ESLint T). **Aucun test n'envoie un vrai email** : transport `memoire` sous Vitest, garde réseau (`tests/garde-reseau.ts`) sur les ports 25, 465, 587 et 2525, transport `fichier` imposé par `playwright.config.ts`. Fiche : `docs/features/envoi-emails.md`.

## Méthode de travail

- Une fonctionnalité correspond à une fiche `docs/features/<nom>.md`, validée avant d'écrire le code : contexte, problème, solution retenue, sécurité et permissions, critères d'acceptation, tests, statut.
- Les tests d'abord : écris les tests, dont les tests d'attaque des menaces citées dans la fiche, montre qu'ils échouent, puis implémente.
- Avant de dire qu'une tâche est terminée : `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, et `npm run test:integration` sur `dev` si la base est concernée. Montre les sorties. N'affirme rien sans preuve.
- Ne modifie que les fichiers du périmètre de la tâche. Si un autre changement semble nécessaire, demande.
- Ne modifie jamais une migration déjà appliquée, ni le dossier `drizzle/` à la main. **Seules exceptions écrites**, deux formes de migration personnalisée :
  - une migration créée par `npx drizzle-kit generate --custom --name forcer-isolation-<table>`, dont le seul contenu est une ou plusieurs lignes `ALTER TABLE "<table>" FORCE ROW LEVEL SECURITY;` ;
  - pour une table en ajout seul, une migration créée par `npx drizzle-kit generate --custom --name retirer-droits-<table>`, dont le seul contenu est une ou plusieurs lignes `REVOKE UPDATE, DELETE, TRUNCATE ON TABLE "<table>" FROM "app_facturation";`. Jamais `GRANT`. Fiche : `docs/features/journal-audit.md`, section 2.2.

  Dans les deux cas, l'assistant crée le fichier vide par la commande et indique la ligne exacte ; le développeur la colle. L'assistant n'écrit jamais dans `drizzle/`.

- Une branche par fonctionnalité (`feat/...`, `fix/...`). Commits au format `type(portée): message`, en français.
- Interface en français, textes regroupés dans des fichiers dédiés (NF-01).
- En cas de doute sur une exigence, demande. N'invente pas de règle métier.

## Pièges connus

- Drizzle 1.0 en version candidate avec Better Auth : utiliser `@better-auth/drizzle-adapter/relations-v2`. Le fichier `src/server/db/schema/auth.ts` est généré, ne l'édite pas à la main. Pour le régénérer : l'outil refuse une configuration qui mène à `import "server-only";`. Retire temporairement cette ligne de `src/server/auth/config.ts` et de tous les fichiers de `src/server/` qu'il importe, directement ou non (aujourd'hui `src/server/db/client.ts`, `src/server/env.ts`, `src/server/env-schema.ts`), lance `BETTER_AUTH_TELEMETRY=0 npx auth@<version de better-auth> generate --config src/server/auth/config.ts --output src/server/db/schema/auth.ts --yes`, rétablis les lignes, lance `npx prettier --write src/server/db/schema/auth.ts`, puis vérifie par `git diff --stat` que seuls `auth.ts` et, le cas échéant, `config.ts` ont changé. **Toujours `auth@<version exacte>`, égale à celle de `better-auth` dans `package.json`, jamais `auth` seul ni `@latest`** : le nom `auth` existe depuis 2012 et a changé de propriétaire, et l'outil tire des dépendances à versions flottantes. Constaté le 2026-10-08 avec `auth@1.7.7` : l'outil charge lui-même `.env` puis `.env.local` avant la configuration, sans écraser une variable du terminal ; aucune variable du projet n'est à définir. `config.ts` charge `env.ts` : les trois variables de `.env.local` doivent être valides. Pour passer des identifiants `text` aux `uuid` sans conversion sur place, la marche suivie est décrite dans `docs/features/identifiants-uuid.md`, section 3.2.
- Connexion groupée de Neon : l'organisation active se fixe avec `set_config('app.organisation_id', ..., true)` à l'intérieur d'une transaction. C'est le rôle d'`executerDansOrganisation`, à ne jamais contourner.
- Marque de la base de test : le commentaire de base exact `environnement:test`, posé par `scripts/retablir-acces-dev.mjs` (sur `dev`) et `scripts/preparer-base-test.mjs` (en CI). `ALTER DATABASE ... SET` est refusé par Neon. Une branche `dev` recréée perd la marque : les tests d'intégration refusent alors de tourner, c'est voulu. Ne jamais poser la marque sur `preview` ni `production`.
- Outillage des tests avec base : `src/server/db/outils-test/`, importable seulement depuis un fichier de test (règle ESLint). Toujours enregistrer `nettoyer` par `onTestFinished` ou `afterAll`. Une table en ajout seul se passe à `creerDeuxOrganisations` par `tablesAjoutSeul`, jamais par `tables` : le rôle de l'application ne peut pas en supprimer les lignes, et `nettoyer` laisse alors sur `dev` les organisations qui y ont écrit (environ 4 par exécution, accepté). Seuls `src/server/db/**/*.test.ts` peuvent importer `db` et `drizzle-orm` : un test d'intégration qui en a besoin vit dans `src/server/db/`.
- Membres et sessions réelles en test : `creerMembre` et `nettoyerMembres` (`outils-test/membres.ts`). Dans `afterAll`, appeler le `nettoyer` des organisations d'abord, puis `nettoyerMembres` dans un `finally` : un échec ne laisse alors aucune organisation sur `dev`.
- Connexions en CI : le PostgreSQL de la CI accepte 100 connexions (97 pour un rôle ordinaire, 3 étant réservées aux super-utilisateurs), **sans regroupement**, alors que `dev` passe par celui de Neon, qui accepte des milliers de clients. Un test qui ouvre trop de connexions passe donc sur `dev` et échoue en CI (`53300`, « too many clients already »), y compris dans un autre fichier lancé en parallèle. Chaque fichier de test a son `Pool` principal (10 au plus), Vitest lance `availableParallelism() - 1` fichiers à la fois, et `pg` ne rend une connexion inactive qu'au bout de 10 s. Un `Pool` dédié se ferme à la fin du test qui l'a ouvert (`onTestFinished(() => pool.end())`), jamais seulement en `afterAll`. Constaté le 2026-10-11 : deux `Pool` de 50 du même fichier, ouverts ensemble.
- PostgreSQL 18 renvoie `23001` (et non `23503`) pour une suppression refusée par une clé en `ON DELETE RESTRICT`.
- Zod 4 donne le même type à `z.object` et à `z.strictObject` (`$strip` et `$strict` ont la même forme) : un type ne peut pas exiger un schéma strict. `declarerAction` le vérifie à l'exécution (`docs/features/chaine-controles.md`, section 3.2).
- Échappement dans `eslint.config.mjs` (rencontré aux fonctionnalités 0.2, 0.3 et 0.4) : dans une expression régulière d'esquery (sélecteur de `no-restricted-syntax`, `chargementsDynamiques`), la barre oblique s'écrit `\\u002F` et le point `\\.` dans le source, avec **deux** barres inverses ; un motif de `no-restricted-imports` (`regex`) écrit `\\.` aussi. Avec une seule, la chaîne JavaScript donne une barre oblique nue, qui termine l'expression (`Invalid regular expression: /(^|/: Unterminated group`) : toute la configuration devient invalide et tous les tests de `regles-import.test.ts` échouent, règles A à F comprises. Cause constatée : les outils de l'assistant (heredoc, outil d'édition) réduisent `\\` à `\` et convertissent `\u002F` avant l'écriture. Façon sûre : écrire ces lignes par un script Python qui construit la barre inverse (`b = chr(92)`, puis `b + b + "u002F"`), en recopiant la forme des lignes existantes ; compter ensuite les barres inverses de chaque ligne qui contient `u002F` ou `action$` (toutes doublées) ; puis lancer `regles-import.test.ts`.
- Aucune directive `eslint-disable`, `eslint-enable` ni `/* eslint ... */` dans `src/` : `linterOptions.noInlineConfig` les rend sans effet (vérifié par `regles-import.test.ts`). Une exception à une règle passe par une modification de `eslint.config.mjs`, donc par une PR.
- **Jamais de variable Gmail (`GMAIL_*`) dans `.env.local`.** `npm run test:e2e` lance `next start`, donc `NODE_ENV=production`, qui charge `.env.local` : un test de bout en bout pourrait envoyer un vrai email. `playwright.config.ts` impose `EMAIL_TRANSPORT=fichier` et un dossier temporaire à chaque serveur, mais le mot de passe d'application ne vit que dans Vercel (type Sensitive). Une variable `EMAIL_*` présente mais vide est refusée au démarrage : dans `.env.example`, ces lignes restent en commentaire.
- **Configuration d'envoi sur Vercel** (`docs/features/envoi-emails.md`, section 9). Une variable de Vercel ne s'applique qu'au déploiement suivant, quel que soit le code déployé. En production, `EMAIL_TRANSPORT` est facultatif et vaut `smtp` s'il est absent ; toute autre valeur est refusée ; `GMAIL_UTILISATEUR` et `GMAIL_MOT_DE_PASSE_APPLICATION` sont obligatoires (posées en Production depuis le 2026-10-13) : sans elles, chaque requête du site échoue. Ne jamais poser `EMAIL_TRANSPORT` en production : inutile, et refusé par tout code antérieur à la PR 2 de la 0.7. En prévisualisation sans variable : `memoire`. Les variables de prévisualisation (second compte, `EMAIL_TRANSPORT=smtp`, `EMAIL_DESTINATAIRES_AUTORISES`, obligatoire avec `smtp` hors production) ne se posent que pour une branche nommée, et seulement quand cette branche porte le transport `smtp` (étape 8, prévisualisation de la 1.1). Après la fusion de la PR 2 : contrôle immédiat, et retour arrière par « Instant Rollback » si la production tombe (étapes 6 et 7). - Après l'arrêt d'un serveur local par Ctrl+C, vérifier que le port est libre (`netstat -ano | grep ":3000"`) avant de relancer. Un essai a montré des erreurs d'un lancement précédent, sans cause établie.
- **Après l'arrêt d'un `npx next start`, vérifier qu'aucun processus Node ne reste en écoute** : `netstat -ano | grep LISTENING | grep ":3000"` (ou le port choisi). Constaté le 2026-10-12 : arrêter le processus lancé par `npx` laisse vivre le Node enfant, toujours en écoute. Avant de l'arrêter (`taskkill //PID <pid> //F`), vérifier sa ligne de commande : `powershell -NoProfile -Command "(Get-CimInstance Win32_Process -Filter 'ProcessId=<pid>').CommandLine"`.
- **Rendu dynamique obligatoire** : le gabarit racine appelle `await connection()`. Une page préconstruite n'a pas de nonce, et la politique bloque ses scripts (page non hydratée). Ne jamais activer `cacheComponents` ni le prérendu partiel (`docs/features/socle-interface.md`, section 5.2).
- **`Referrer-Policy` reste `same-origin`, jamais `no-referrer`** : sous `no-referrer`, un `POST` vers la même origine part avec `Origin: null`, que la chaîne de contrôles refuse ; toutes les actions serveur seraient refusées (`docs/features/socle-interface.md`, section 6).
- **Une configuration refusée fait échouer chaque requête**, et pas seulement les modules qui importent `env.ts` : `register` lève, et toute réponse devient un 500 `Internal Server Error`, `/` comprise (constaté le 2026-10-12, Next.js 16.3.8). `register` n'attrape pas cette erreur, volontairement. Un serveur de test en panne se monte avec une configuration valide et une base injoignable (`docs/features/socle-interface.md`, section 4.3).
- Test d'affichage dans un cadre : une page fournie par `route.fulfill` de Playwright est vue par Chromium comme publique, et il refuse qu'elle charge `localhost` (`ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS`) : le test passerait sans aucun en-tête. Servir l'autre origine par un vrai serveur `node:http` sur `127.0.0.1` (`e2e/entetes.attaque.spec.ts`).
- **Dossier `.next/dev/types` périmé après le déplacement ou la suppression d'une page** (constaté le 2026-10-12, `src/app/page.tsx` déplacé dans `(public)/`). `tsconfig.json` inclut `.next/dev/types/**/*.ts`, écrit par `next dev` et que ni `next typegen` ni `next build` ne réécrivent : son `validator.ts` cite encore l'ancienne page, et `npm run typecheck` comme `npm run build` échouent (`Cannot find module '../../../src/app/page.js'`). Remède : supprimer `.next/dev` (dossier généré, ignoré par git), ou lancer `next dev` quelques secondes pour qu'il le réécrive, puis arrêter le serveur et vérifier le port. La CI n'a pas ce dossier.
- **Une erreur de rendu serveur ne met pas la page « erreur » dans le HTML** (constaté le 2026-10-12, Next.js 16.3.8). Une erreur levée hors d'une frontière Suspense (par exemple `ErreurPage` dans `(app)/layout.tsx`) fait échouer le squelette : Next.js renvoie son document d'erreur, `<html id="__next_error__">`, statut 500, au corps vide, avec la politique et les en-têtes ; la charge utile n'y porte que `E{"digest":"..."}`. `error.tsx` n'est rendu que dans le navigateur, après hydratation : sans JavaScript, page blanche. Un test qui lit le HTML brut ne trouve donc pas « Une erreur est survenue. » ; il vérifie le document d'erreur et le `digest`, et le texte se vérifie dans le navigateur (`e2e/erreurs.attaque.spec.ts`, `docs/features/socle-interface.md`, section 4.3).
- **`uqr` ne s'importe que dans `src/server/auth/qr.ts`** (règle ESLint V, 1.4) : le navigateur ne reçoit que la matrice du code QR. Le secret TOTP n'est jamais relu (`/two-factor/get-totp-uri` fermé) ; la remise à zéro manuelle de la double authentification suit `docs/exploitation/remise-a-zero-double-authentification.md`, exécutée par le développeur seulement.
- **Horloge avancée dans un test d'intégration** (`vi.setSystemTime`, constaté le 2026-10-21) : à chaque `findVerificationValue`, Better Auth supprime **toutes** les lignes de `verification` dont l'échéance précède son horloge, celles des autres fichiers lancés en parallèle comprises. Avec `+10 min` (`double-authentification.integration.test.ts`), des lignes encore valables disparaissaient ailleurs (sonde : 8 sur 172 en deux minutes). Un banc dont le fichier avance l'horloge se crée avec `horlogeSimulee: true` (`outils-test/inscription.ts`, `disableCleanup`).
- **Comparer deux réponses d'une même route avec une session** (`e2e/zones.attaque.spec.ts`, test 31) : le découpage du flux RSC en balises `<script>` et l'ordre de ses lignes suivent la durée des lectures en base, qui varie ; `documentServi` compte ces balises. Utiliser `documentEtFlux` (`e2e/outils.ts`), qui compare le contenu du flux, trié, et jamais deux adresses différentes (le flux nomme l'adresse).
